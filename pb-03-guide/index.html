Hand repeat work to one playbook

When the same task comes back, skip the new agent. Write the job once, keep the files you already trust, and make the model show its work before you take it back.

I'm Ahmed. This is the written version of the loop I use when a task shows up again. Open a blank folder. By the end of the first pass you should have a playbook you can run.

What this is, and what it is not. The loop on this page is a way to teach repeat work. Anthropic's Agent Skills docs use a folder of instructions plus a file named SKILL.md. They have not dropped agents, and some jobs still want more than one. Use this when the work repeats and you want one clear set of instructions first.

Where a pile of agents breaks

The usual start is excitement. An agent for mail, another for posts, one for research, one for chasing replies. Pretty soon you are keeping four half-built setups. Each setup carries a separate prompt, a separate pile of files, and its own quirks. Change the way you work and you have to patch every setup by hand.

A newer model is often not the missing piece. The missing piece is how you already do the job: the call you make without noticing, the file you open first, and the last look you give something before it goes out.

A calmer start is one strong AI setup, with separate instructions for each job. Anthropic packages that kind of reuse as Agent Skills: written directions, scripts, and the notes that sit beside them. That is a starting point, not a rule that one agent wins every technical problem.

When a run goes wrong, edit the playbook that owns that job. A correction left inside one chat will not be there next time.

Pick one job before you write anything

Leave the hardest job in the business for later. Choose work you do at least once a week, work where a bad result is obvious to you, and work you could teach a coworker in one short conversation.

A weekly client note, a long video cut into short posts, a reminder for an invoice that is past due, or a first pass over applications with a scorecard you already agreed: any of those is a fair first job.

Where the playbook sits

Claude Code, or any tool that can touch files: Create the folder on disk, or inside a repository you control. With the right permission, the model can create the files and update them.

ChatGPT or Claude in the browser: keep the master folder on your computer or in Drive. Bring the current files into the chat when you start. Unless that product writes back to the folder for you, a new draft in the chat does not replace the master. Save the new text, then refresh the copy the chat is using.

One folder is the master. Do not keep two competing copies of the same playbook. Leave passwords, API keys, and private personal details out of any folder you might share or push to a public repository.

Part 1

The steps: get the real workflow onto the page

The playbook starts as an interview. Have Claude, or ChatGPT, interview you. Cover what sets the job off, which files you touch, the order you work in, where you use judgement, and the mistakes that already happened.

The interview matters because the automatic parts are the ones you skip. Maybe a client note always opens on the biggest movement in the numbers. Maybe a reel does not go out until you have said the hook out loud. Those habits are what make the output look like your work.

If you want a Skill that Claude can load, put a short description and the instructions in SKILL.md. If you are only using chat, a normal Markdown file with the same contents is still worth keeping, even if nothing installs it as a Skill.

Prompt 1: interview, then write the playbook

Prompt to paste · 01 / Interview and steps
Turn one task I repeat into a written playbook the model can follow next time.

The task: [NAME THE JOB YOU REPEAT].

Start by interviewing me. Ask a single question, then wait. Do not write the playbook until we have talked through all of this:
- what kicks the task off, and how often it comes back
- which inputs I need, and where I get them
- the steps, in the order I really do them
- where I choose, and the rule I am applying when I choose
- how I can tell a good result from a bad one
- tone, layout, and who it is for
- mistakes I have already made, odd cases, and exceptions
- the last checks I do before I call it finished

If an answer is fuzzy, ask again. Before you draft, ask whether I want to add anything.

When I tell you the interview is done, give me:
1. A short job title, plus a concrete line on when this playbook should be used.
2. A full playbook in the shape of SKILL.md. Include why it exists, when to run it, what it needs, the steps, the choice rules, what finished means, and the exceptions.
3. A list of files or references that still need to be created.
4. Two questions for me: where did you misunderstand the job, and what did I fail to mention?

When file access is available, create [JOB-NAME] and save SKILL.md inside that folder. When it is not, show the full text and name the path where I should put it. If the file is not on disk, do not tell me it is.

Tip: if you plan to install this as a Skill Anthropic's tools can load, add YAML frontmatter at the top of SKILL.md, with the name field and the description field filled in.

Part 2

The files: stop rebuilding the pieces you trust

The file layer is the material the job keeps needing. When a template, a script, a checklist, or a sample you approved actually works, save a version you can reuse. Mention that file inside the playbook, and spell out the moment to open it.

Without that layer, the model may invent a new email shape, a new caption pattern, or a new spreadsheet script on every run. The same effort gets repeated, and the output drifts a little each time.

What is worth saving

  • Scripts that do one predictable step the same way each time.
  • Templates with blanks for the details that change per run.
  • Samples you have already approved, so the bar is visible.
  • Reference notes, including names, spellings, and the words you use.
  • Voice notes for the brand, and smaller prompts you run inside the job.

Leave out drafts you have not signed off, results you will not need again, login secrets, and anything you would not want a coworker to copy blindly.

Prompt 2: save the files you will need again

Prompt to paste · 02 / Files worth keeping
Review the run we just completed, together with the written instructions in [JOB-NAME].

Point out anything we built that we will probably need on the next run: a script, a template, a checklist, wording I already approved, a data note, or a prompt I would reuse.

For every item worth keeping:
1. Pick a clear filename and store it in a files folder inside [JOB-NAME].
2. Swap details that belong only to this case for obvious [PLACEHOLDERS]. Keep one filled example that I have already approved, if that helps.
3. Point to that file from SKILL.md by name, and say when to open it.
4. In INDEX.md under files/, add a row that lists the filename, what it is for, and the date I reviewed it.
5. Leave out one-off drafts, wording I have not approved, passwords, private keys, and secrets.

Run the job again with those files in place. Report which saved files you opened again, and which parts you still had to create on the spot. If you had to create something again, name one more file worth keeping.

Without file access, print every proposed file in full, name its path, and print the updated index. Only say a file is saved after it is really on disk.

File sets for four jobs

Long content into posts

A bank of hooks, a shape for captions, notes on voice, a few reference reels, and a line on why those openings held attention. Save them as hooks.md, post-shape.md, and voice-notes.md.

Weekly client notes

A script that gathers the figures, a skeleton for the note, a spelling list, rules for tone, and two notes you have already sent and still stand by. Save them as pull-figures.py, note-skeleton.md, name-spellings.md, and sound-rules.md.

Invoice reminders

Mail you have approved for an early nudge and a later one, a written path for what happens if it stays open, contact records kept somewhere private, and a note on tone.

Hiring screens

role-note.md, rubric.md, sample reviews you have approved, and one reply template you use every time. A person still has to sign off when the decision affects a real applicant.

Part 3

The checks: say what finished means in a way you can test

Telling a model to "check your work" and hoping it notices is a weak plan. A useful check names something that can be tested without trusting how sure the model sounds.

A real check leaves evidence. A figure agrees with the file it came from. The link has to load. The length has to sit inside the cap you set. A test you run on the code comes back green. A statement lines up with a note you already trust. A check that has no way to fail is too soft to keep.

Prompt 3: add checks that can fail

Prompt to paste · 03 / Checks
On the [JOB-NAME] instructions, add two sections: what finished means, and the checks that prove it.

Write 5 to 10 checks that fit this job. Each check needs a pass or a fail that does not depend on how confident you feel. The evidence has to come from somewhere other than your own judgement.

Useful evidence looks like this:
- a figure matched against the source file
- a link that really opens
- a screenshot of the thing as it actually rendered
- a code test you executed, with a passing result
- a claim tied to a named source
- a count, a filename, or a spelling compared with a reference list

Skip checks that only say the work "seems fine" or "feels polished".

On later runs of this playbook:
1. Do the job.
2. Run every check you can.
3. Fix what fails, then run the checks again.
4. Mark each check as PASS or FAIL or NOT VERIFIED, and attach the evidence.
5. Say plainly what you could not check. Never claim a test executed, and never claim a link opened, unless you really did that.
6. If a cluster of related checks fails, stop. Name the process problem underneath before you polish the wording.

Put these rules into SKILL.md. If you cannot edit files, print the whole revised section and tell me where it belongs.

Checks that are specific enough

Posts: the hook stays inside the word limit you set, the spoken script lands inside the length you wanted, at the pace you had in mind, claims line up with their sources, and the closing line uses the keyword you approved.

Client note: every figure agrees with the original data, the name in the note is the one on the spelling list, and every open action from last time is answered.

Invoice reminder: the amount, the due date, and the recipient match the records, the payment destination was checked, and the tone fits how late the invoice is.

Hiring screen: each score points at something actually written in the application, and missing or uncertain facts are flagged instead of filled in.

The loop: change the playbook, leave the chat alone

When a draft is wrong, the easy move is to answer "try again, you missed the brief" and carry on. Next time the same job runs, the same miss comes back, because that fix never made it into the playbook.

Call the layer by name. If a step was never written down, that is the steps layer. If a saved file is stale, or the model rebuilt a template from nothing, that is the files layer. If a check should have caught the miss and did not, that is the checks layer.

Prompt 4: find the miss and patch the file

Prompt to paste · 04 / Diagnose and repair
The latest [JOB-NAME] result missed. The specific miss: [DESCRIBE THAT ERROR].

Do not stop at a patched chat reply. Name the layer:
- PROCESS: a step, a choice rule, or an exception was absent, or it was stated badly.
- TOOLBOX: a file you meant to reuse was absent, out of date, chosen poorly, or created again for no reason.
- PROOF: no check covered this miss, or the check existed and still let it through.

State the cause in a few lines, then name the smallest change that should stop a repeat.

After that:
1. Change the section or file that is actually wrong. Leave the rest of the playbook alone.
2. If this same mistake has happened twice, add a direct rule that blocks it.
3. Write a dated line in notes.md inside [JOB-NAME], covering the error and the fix.
4. Run the job again, including the checks.
5. Place the earlier result next to the new one, and say whether the fix held.

If editing is blocked, show the replacement text and the path. The fix is not lasting until that source file on disk has been edited.

Read the correction notes on a regular pass. If the same layer keeps failing, that layer needs more than another chat nudge. Spend the next pass on a sharper rule, a stronger template, or a test you can execute with a script.

The folder after you have built it

A separate folder for each job makes the matching instructions easier to spot. Write the description the way you would actually ask for that job.

client-week-note/ ├── SKILL.md # when to use it, inputs, order of work, │ # choice rules, and how you test done ├── files/ │ ├── INDEX.md # a list of saved pieces and why they exist │ ├── pull-figures.py # gathers the figures from the source export │ ├── note-skeleton.md │ └── sound-rules.md ├── examples/ │ ├── kept-note-01.md │ └── kept-note-02.md └── notes.md # a log of misses and the edits that followed

If Claude should load this as a Skill, put name and description in YAML at the top of SKILL.md. Ship a script only when the model can run it safely in that environment, and get a yes before it opens private systems.

A short SKILL.md, filled in

--- name: client-week-note description: Use this when asked for the weekly client results or a short progress note. --- # Weekly client update ## What you need - The reporting file that was already approved - What was promised the week before - The client's name spelling and style notes ## Order of work 1. Open the latest approved report file. 2. Line the numbers up against the target and the prior week. 3. Draft from files/note-skeleton.md. 4. Match every figure back to that source file. ## Finished means - Each number agrees with the source. - The name in the note is the one on the spelling list. - Each promise from last week is answered. - If a number is missing, say so. Do not invent one.

Walkthrough: a weekly client note

Steps. During the interview, spell out this order: start in the ads dashboard, set last week's numbers against the plan, lead with the largest movement, and write the note in a plain voice. That order becomes part of the playbook.

Files. Once a run is good enough to keep, store the script that gathers the numbers, the skeleton of the note, a spelling list, and a sample you still like. Link each item so the model knows where to look.

Checks. Every figure has to agree with the source. The note has to stay inside the length you set. The client name has to match the spelling list. Last week's promise has to be answered.

Loop. Picture a follow-up note that cites a figure the dashboard does not contain. Log the miss under checks, write a rule that each figure must be present in the source, and run the note once more. The point of that extra run is to see the rule catch the bad figure. Asking the model to try harder is not enough.

Over time, more of the sitting should go to reading the result in front of you, and less of it to saying the same directions again. A person should still approve anything that leaves the building, and any choice with real stakes.

Five traps

  1. Drafting the steps from memory alone. Use the interview to surface the real choices and the odd cases.
  2. One giant folder for every task. Give each job its own folder so the right notes are easy to open.
  3. A fuzzy description of when to use the playbook. Say the exact moment this file should be opened.
  4. Skipping the checks. "Seems fine" is not evidence the task was done.
  5. Correcting the chat and stopping. Change the master file, then run the job again and see if the fix is still there.

A first sitting

Start with one task you do on a regular schedule. Treat half an hour as a sensible first sitting, not a promise that a complicated job will be fully written and tested that fast.

The second run is the one that shows what you can trust on the next run, what is still fuzzy, and which checks are too loose. Do not stop when the first write-up is done.
